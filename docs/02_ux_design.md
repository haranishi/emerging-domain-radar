# ユーザーストーリーと UX 5 階層 — Emerging Domain Radar

作成: 2026-09-03（Fable）。実装前に戦略層から書き、設計判断を導くための文書。末尾に「この文書で変わった実装判断」を記録する。

## 1. 想定ユーザー

- 本人（個人事業主・開発とマーケの両方をやる）。毎朝 5〜10 分、ローカルで開く。
- 英語の技術情報は読めるが、毎日 HN / GitHub / arXiv を巡回する時間はない。
- ドメインは「面白そうなら自分でレジストラで買う」。ツールに買ってほしいわけではない。

## 2. ユーザーストーリー（受け入れ条件付き）

| ID | ストーリー | 受け入れ条件 |
|---|---|---|
| US1 | 朝ダッシュボードを開き、今日の候補を調査優先度順に 1 分で眺めたい | 初回描画で上位カードが順位・Status・3 スコア・根拠 3 行・ドメイン 3 件を含む。スクロールだけで 20 件見られる |
| US2 | 「なぜ候補なのか」を数字で確かめたい | 詳細画面に ソース×窓 の件数表と増減率、元ソースの検索リンクがある。AI の説明は「推測」と表示が分かれている |
| US3 | 候補の .com が空いているか・いくらか・更新はいくらか・Premium か、を一目で知りたい | ドメイン行に AVAILABLE/TAKEN/UNKNOWN、登録価格、更新価格、Standard/Premium、確認時刻、価格取得元、公式サイトリンク がある。取れないときは `Price unavailable` |
| US4 | 思いついたドメインを直接（複数まとめて）調べたい | `/search` にテキストエリア。改行・カンマ区切りで最大 20 件を一括判定 |
| US5 | 条件で絞りたい（空きのみ・$20 以下・Emerging のみ 等） | フィルターは URL クエリに反映され、リロードやブックマークで再現できる |
| US6 | 気になった候補を覚えておき、価格が変わったら気づきたい | Watchlist に保存。発見時価格と現在価格を並べ、履歴が増える |
| US7 | 間違って買う事故が起きないと確信したい | 購入系の画面・ボタン・API が存在しない。About に「このツールから購入はできない」と明記 |
| US8 | 収集は自分のタイミングで（将来は毎日自動で）回したい | `npm run radar:collect` 1 コマンド。未収集時のダッシュボードにその手順が出る |
| US9 | 有料 API を契約しなくても使い始めたい | キー 0 個で収集が完走し、ダッシュボードに候補が出る（ソースは HN / GitHub / arXiv / OpenAlex / Qiita / Google News） |

## 3. UX 5 階層

### 3.1 戦略層（なぜ作るか・何を成功とするか）

- ユーザー価値: 「見つける → 空きと価格を知る → 判断する」の往復を 1 か所で終わらせる。
- 事業価値: 早期に良い一般名詞 .com を安価に押さえる機会を逃さない。ただし判断は人。
- 成功指標: 1 候補あたりの判断時間 1 分以内／根拠が追える（リンク到達 1 クリック）／毎日開く。
- 信頼の設計: 数値根拠・取得時刻・取得元を必ず見せる。AI 生成文は推測として色分けする。
- 安全の設計: 購入導線ゼロ。金額は「調査優先度」に影響するが「買え」とは言わない。

### 3.2 要件層（何を載せるか）

- コンテンツ要件: キーワード／説明／Status／Trend・Japan Gap・Novelty・Domain・Opportunity／Evidence（ソース×窓）／関連語／ドメイン候補（空き・価格・更新・Premium・確認時刻・取得元・公式リンク）／商標注意とリンク／為替（レート・取得元・時刻）／最終収集時刻。
- 機能要件: `01_requirements.md` の F1〜F18。
- 表示ルール: 価格は `$11.06 / yr` の形。JPY は小さく `≈ ¥1,650（ECB 2026-09-02 15:00 UTC）` の形。取れない値は `Price unavailable` / `—` を使い、0 や推測値を出さない。

### 3.3 構造層（情報の配置と導線）

- ルート:
  - `/` Dashboard（ランキング＋フィルター）
  - `/keywords/[slug]` キーワード詳細
  - `/search` 手動ドメイン検索（一括）
  - `/watchlist` Watchlist
  - `/about` スコアの計算方法・データソース・制限・購入不可の明記
- 導線: カード → 詳細 → ドメイン行の公式リンク（外部・新規タブ・`rel="noopener noreferrer"`）。詳細から「Watchlist に追加」。
- 状態: フィルターは URL クエリ。Watchlist と収集結果は SQLite。為替はサーバーで 1 時間キャッシュ。

### 3.4 骨格層（画面の骨組み）

- Dashboard: ヘッダー（タイトル `Emerging Domain Radar`／最終収集時刻／候補数）→ フィルターバー（上部固定）→ カード列（順位、キーワード、Status バッジ、3 スコアの数値＋短いバー、Why trending 3 行、ドメイン 3 行＋「+N more」、Last checked）→ 空状態（未収集なら実行コマンドを表示）。
- 詳細: 見出し（キーワード／Status／スコア 5 種）→ 説明と「なぜ候補か」（推測ラベル）→ Evidence 表（行=ソース、列=直近 7 日／前 7 日／増減／直近 30 日／前 30 日／増減／リンク）→ いつから増えたか（初出日）→ 関連語 → ドメイン候補表（全件。空き／登録／更新／種別／Domain Score／確認時刻／取得元／公式リンク／Watchlist 追加）→ 商標注意ブロック（4 つの検索リンク）→ スコア内訳（式の各項の値）。
- Search: テキストエリア → 判定ボタン → 結果表（同じ列構成）→ 各行に Watchlist 追加。
- Watchlist: 表（キーワード／ドメイン／発見日／発見時価格／現在価格／差分／Trend／Opportunity／削除）。
- About: 式・閾値・ソース一覧・制限事項・「購入はできません」。

### 3.5 表層（見え方）

- 情報密度は高め、装飾は最小。等幅フォントでドメインと価格を揃える。
- Status バッジ: Early=グレー、Emerging=緑、Rising=青、Trending=琥珀、Mainstream=スレート。
- 空き: AVAILABLE=緑、TAKEN=赤、UNKNOWN=グレー。Premium は琥珀のタグ。
- ダーク／ライト両対応（システム設定に追従）。
- 文言: UI ラベルは英語（仕様の例に合わせる）、注記・免責は日本語。

## 4. この文書を通したことで変わった実装判断（実装前に確定）

1. フィルター状態を React の内部 state ではなく **URL クエリ** に置く（US5・構造層）。
2. ダッシュボードのカードは **ドメイン 3 件だけ**表示し、残りは詳細へ（US1・骨格層の走査速度）。
3. Evidence の各行に **元ソースの検索 URL** を必ず付ける（戦略層の信頼設計）。数字だけの表は不可。
4. 収集は **UI のボタンではなく CLI**（US8・レート制限のある長時間処理を UI から起こさない）。ダッシュボードは最終収集時刻と空状態の手順だけ持つ。
5. 価格表示は **取得元と確認時刻をセット**で出す。取れないときは `Price unavailable`（要件層の表示ルール）。
6. Premium 判定は API があれば API、無ければ **`Standard (inferred)` と根拠文**を表示（US3・信頼設計。断定しない）。
7. 商標は **除外辞書＋4 リンク＋常時注意文**の 3 点セット（US7・戦略層の安全設計）。「安全」の表示は作らない。
8. Watchlist は P1 だが **今回実装**（US6・データモデルに価格履歴テーブルを最初から持つ方が安い）。
9. `/about` を追加（US7・スコア式と購入不可を UI 内で確認できる場所を作る）。
10. AI 生成の説明文は **「推測」バッジ付きの別ブロック**にし、数値 Evidence と混ぜない（US2）。
11. オフラインモード `RADAR_OFFLINE=1` を最初から設計に入れる（E2E とスクショ採点をネットワーク無しで決定的に回すため）。
